# ADR 0002：Android 主界面改为高保真桌宠监控

## 状态

已接受

## 日期

2026-05-29

## 背景

用户的核心痛点不是缺少一个红黄绿颜色，而是不知道多个 Codex 项目现在处在什么情况：可能正在推进，可能网络卡住，可能等待权限，可能要求用户互动，也可能 Codex 已经缩到后台。旧手机摆在旁边时，界面还需要有装饰性和可持续观看的亲和力。

红绿灯主视觉可以表达粗略状态，但过于基础，也容易让连接状态、项目状态和介入需求混在一起。

## 决策

Android 主界面从“红绿灯”改为 BSOD 蓝屏桌宠监控：

- 顶部保留 BLE 连接状态，连接状态不参与业务状态颜色语义。
- 主视觉优先使用 Codex app 自带的 BSOD spritesheet，显示蓝色屏幕脸、白色机身、短天线、粉色脸颊和小手小脚。
- BSOD spritesheet 作为本机专有资源同步到 `android/app/src/main/assets/codex_bsod_spritesheet.webp`，不提交进仓库；资源缺失时回退到内置绘制版本。
- 项目整体情况通过桌宠 mood 和中文短句表达。
- 项目列表改为极简行列表，按需要关注优先排序，再按最近活动时间排序。
- 背景和面板尽量使用纯黑，减少标题、方框和长说明，只有眼睛、胸屏、连接状态和项目提示使用少量亮色，适配旧手机常亮和 OLED 省电。
- 桌宠保持中等尺寸，并加入低幅度呼吸、上下浮动和轻微摆动，避免常亮时像静止图片。
- Android 端允许用户在手机上隐藏项目，并在隐藏列表中恢复；隐藏集合只存在手机本机，不改变 BLE payload 或 Mac companion 状态。
- BLE 协议和 Mac companion 状态聚合逻辑保持不变，继续使用 `g/y/r` 紧凑状态码作为传输层契约。

## 依据

- 用户希望“偏可爱桌宠”，旧机器摆在那里也能作为装饰。
- 用户明确要求“能全黑的都全黑”，因此视觉层需要优先考虑省电和低亮度常亮。
- 用户认可 Codex 自带桌宠的 BSOD 蓝色方向，因此 Android 主视觉应尽量复用原版 spritesheet，而不是手绘仿制。
- 真正需要被看见的是“是否需要用户介入”，不是单个颜色。
- 传输层状态码已经能满足 v1 数据需求，当前问题集中在 Android 表达层，不需要为了 UI 改协议。

## 后果

正向影响：

- Android app 的第一视觉更符合桌面陪伴设备，而不是单纯状态灯。
- 中文状态短句更直接表达“推进中 / 刚动过 / 需要看一眼 / 阻塞 / 离线”。
- BLE 协议保持兼容，Mac companion 不需要重新配对或改变服务 UUID。

取舍：

- `Codex Traffic` 设备名和 `g/y/r` 协议字段暂时保留历史命名，避免破坏已验证的 BLE 契约。
- 机器人 mood 仍基于现有启发式状态，不承诺等同 Codex 内部私有运行态。
- v1 仍是前台 Android app，不做后台 service 或系统通知。

## 验证

- Android Compose 测试改为断言旧标题/看板已移除、`pet_bot`、`bot_summary` 和中文项目状态。
- Android 单元测试继续覆盖 payload parsing 和 ViewModel 状态流。
- 构建验证使用 `./gradlew testDebugUnitTest assembleDebug`。
